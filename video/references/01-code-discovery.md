# 01 · 源码勘察：从代码读出「该讲什么」

目标不是"读懂代码"，而是**产出一份可讲的业务大纲**。视频的观众要听懂的是「这个系统在做什么、为什么这么设计、边界在哪」，不是类怎么继承。

> ### 先确认源码目录（技能的第 1 个必问点）
>
> 开工前必须拿到**具体路径**，并问清三件事：
> 1. **单仓库还是多仓库**（前后端是否分开）—— 分开了要拿到两边的路径
> 2. **有没有要排除的目录**（`node_modules`、`dist`、`vendor`、第三方 SDK 源码）
> 3. **对应哪个分支 / 版本** —— 讲解要对齐一个确定的版本，别拿主干去讲生产上的行为
>
> 拿到后先跑阶段 A，**把代码量报给用户**再决定怎么读（见 A1 的档位）。

---

## 阶段 A：先摸清底细（10 分钟内完成）

按顺序做，不要跳。每一步都只取"能影响讲解口径"的信息。

### A1 技术栈与规模

```bash
# 顶层清单
ls -la
# 依赖与语言（按存在的那几个看）
cat package.json pom.xml build.gradle requirements.txt go.mod composer.json 2>/dev/null
# 目录树（只看两层，别急着深挖）
find . -maxdepth 2 -type d -not -path "*/node_modules/*" -not -path "*/.git/*" | sort
# 代码量：判断是万行级小系统还是十万行级大系统
```

- 代码量 < 3 万行：可以逐模块读
- 3 万 ~ 15 万行：按"业务动作"抽，不看全部
- > 15 万行：**必须先问用户要讲哪个子系统**（这就是技能的第一个必问点存在的原因）

### A2 找入口

| 形态 | 去哪找 |
|---|---|
| Spring Boot | 带 `@SpringBootApplication` 的类；`application.yml` 的 `context-path`；`@RestController` 上的 `@RequestMapping` |
| Node/Express | `app.js` / `server.ts` 里的 `app.use`；`routes/` 目录 |
| Vue / React | `src/router/index.*`；`src/views` / `src/pages`；`src/api/*` |
| 小程序 | `app.json` 的 `pages` / `tabBar` |
| 桌面 Electron | `src/main/index.ts`（主进程）、`preload`、`renderer/src/router` |
| 传统 Java Web | `web.xml`、`struts.xml`、`applicationContext.xml` |
| Python | `manage.py` / `main.py` / `app/routers/*` |

### A3 提取业务名词（这一步最关键）

**业务名词藏在配置里，不在代码逻辑里。** 优先读：

1. **路由表 / 菜单配置** —— 几乎等于系统的功能清单，而且是被人挑过的措辞
2. **权限表 / 角色-资源映射** —— 能看出"谁的活"和"哪些动作是敏感的"
3. **枚举与数据字典常量** —— 状态机、类型、优先级。状态流转顺序往往就是主流程
4. **数据库 DDL 或实体类** —— 领域对象和它们的关系
5. **定时任务 / 消息队列消费者清单** —— 系统里"自动发生的那些事"
6. **外部接口对接清单**（`feign` / `HttpClient` / `axios` 封装）—— 系统边界在哪

把这些名词按"业务动作"聚合，而不是按"技术层次"聚合。

> 反例：*"这个模块用了工厂模式、策略模式，还有三层缓存"* —— 观众不关心。
> 正例：*"订单一进来先冻结额度，再拆成多个履约单，最后按仓分派"* —— 这才是业务。

### A4 每条候选链路补四个信息

| 字段 | 从哪来 |
|---|---|
| 一句话定位 | 路由/菜单名 + 你自己的归纳（≤ 20 字） |
| 输入 | Controller 入参 / 事件消息体 / 定时任务触发条件 |
| 输出 | 写库了哪些表 / 发了什么消息 / 返回给前端什么 |
| 关键文件 | 3~8 个路径，作为讲解时的"落点" |

## 阶段 B：产出讲解大纲

### B1 结构模板

```
片头          —— 系统一句话定位 + 这支视频回答什么问题
第 1 章       —— 整体架构（分层 / 模块地图）
第 2..N-1 章  —— 按业务动作排序的主链路（每章一个动作，3~7 章）
倒数第 2 章   —— 关键设计取舍（为什么这么做，代价是什么）
收尾          —— 链路回顾 + 边界声明
```

**章节顺序 = 数据流顺序**，不是代码目录顺序。观众跟着一条请求走一遍，比按包名念一遍有效得多。

### B2 每章只回答三个问题

1. 这一步**做什么**（业务语言）
2. 为什么**这么设计**（取舍 / 约束 / 历史原因）
3. **边界在哪**（不做什么、什么情况下会失败、需要人工介入的地方）

第 3 点最容易被省略，但它恰恰是可信度的来源。能力边界要主动写出来，别等观众发现。

### B3 判断"该讲多深"

| 代码里的东西 | 视频里怎么处理 |
|---|---|
| 业务规则（校验、状态机、审批） | **讲透**，这是系统的价值所在 |
| 数据模型与关系 | 讲，用图表画对象关系 |
| 架构分层与调用链 | 讲，用分层图/流程图 |
| 设计模式、并发细节、性能优化 | 只在"解释为什么这么设计"时提一句 |
| 具体函数实现、SQL 语句、配置项 | 不讲。观众记不住，也不需要 |

### B4 立项前必须跟用户对齐（对应技能里的第 2 个必问点）

把候选讲解对象列出来，让用户选。格式：

```
扫描到 N 个子系统 / 模块：

  A. 订单管理    下单受理 → 库存校验 → 履约跟踪     建议 6 分钟
  B. 库存管理    入库 → 出库 → 盘点 → 预警          建议 5 分钟
  C. 结算对账    账单生成 → 差异核对 → 人工调整     建议 4 分钟
  D. 权限体系    角色 → 菜单 → 数据权限             建议 3 分钟

要讲哪一个？也可以说"全系统的整体架构"。
```

## 阶段 C：给 AI 的辅助提示词（可选，但很省时间）

代码量大时，先用检索把候选缩小，再人工判断：

```
在 <源码目录> 中找出所有"业务功能入口"，输出表格：
| 功能名 | 入口文件:行 | HTTP 路径或事件名 | 涉及的主要数据表 | 一句话业务说明 |

判定标准：
- 业务功能入口 = Controller 的公开方法 / 路由注册项 / 定时任务方法 / MQ 消费者方法
- 排除：工具类、配置类、纯查询辅助方法、DTO/VO 定义、单元测试
- 忽略 `*Test`、`*Config`、`*Util`、`*Helper`、`*Constant` 目录

不要读取全部文件内容，先用文件名、目录名、路由表、注解做初筛。
```

拿到这张表之后，**自己重排顺序并合并同类项**，不要直接把它当大纲——它还是技术视角的。

## 检查清单

- [ ] 能一句话说清这个系统是干什么的（用业务语言，不含技术名词）
- [ ] 每个章节都能回答"做什么 / 为什么 / 边界在哪"
- [ ] 章节数是 3~7 个（超过 7 个说明粒度太细，合并）
- [ ] 没有任何章节是"讲某个技术点"
- [ ] 已把候选清单给用户确认过
- [ ] 总字数符合目标时长（见 03-narrative.md）
