# 03 · 解说稿：字数预算与写法

## 一、时长 → 字数（先算再写，不要写完再删）

配音用微软云扬（`zh-CN-YunyangNeural`），实测语速：

| 语速参数 | 汉字/秒 | 说明 |
|---|---|---|
| `+0%` | 约 5.0 | 偏慢，适合技术密度高的段落 |
| `+6%` | 约 5.3 | **默认**，三支成片都用这个 |
| `+12%` | 约 5.6 | 偏快，仅当内容实在压不下去时用 |

全片时长 = 语音时长 + 首尾留白 + 段间静音，经验公式（默认 `leadIn=1.0s`、`gap=0.7s`、`tail=3.2s`）：

```
全片秒数 ≈ 总字数 / 5.3  +  1.0  +  0.7 × (段数 - 1)  +  3.2
```

反解成预算表（按 8 段算）：

| 目标时长 | 可讲字数 | 建议章节数 |
|---|---|---|
| 2 分钟 | 约 570 字 | 3 |
| 3 分钟 | 约 890 字 | 4 |
| 4 分钟 | 约 1210 字 | 5 |
| 5 分钟 | 约 1530 字 | 6 |
| 6 分钟 | 约 1850 字 | 6~7 |
| 8 分钟 | 约 2480 字 | 7~8 |
| **10 分钟（上限）** | **约 3120 字** | 9~10 |

随时可查：

```bash
python <skill>/scripts/build_audio.py --budget 300     # 查 5 分钟能讲多少字
python <skill>/scripts/build_audio.py --dir <工程> --dry  # 查当前稿子预估多久
```

`--dry` 不调用 TTS，秒出结果。**改稿阶段每次都跑一下**，比合成完才发现超时省事得多。

> 10 分钟是硬上限。超了只有两条路：删内容，或提高 `rate`（最多到 `+12%`，再快听不清）。

## 二、分段结构

### 标准骨架（以 5 分钟 / 6 段为例）

| 段 | 角色 | 字数 | 画面对应 |
|---|---|---|---|
| 片头 | 系统一句话定位 + 这支视频回答什么 | 90~130 | 片头卡（用一张有代表性的界面做底） |
| 第 1 章 | 整体架构 / 模块地图 | 180~260 | 分层架构图 |
| 第 2~4 章 | 主链路（每个业务动作一段） | 各 220~300 | 架构图 + 界面截图交替 |
| 第 5 章 | 关键设计取舍与边界 | 200~280 | 对比图 / 链路图 |
| 收尾 | 链路回顾 + 边界声明 | 100~150 | 链路回顾图 + 落版 |

**章节名要用业务名词**，会显示在左上角章节角标上：`订单受理` / `库存校验` / `结算对账`，不要写 `Service 层` / `数据访问`。

### 一段之内怎么写

段 = 一个连贯的讲述单元，内部按「是什么 → 怎么做 → 边界/取舍」三拍走：

```
第 1~2 句：这一步做什么（业务语言，给结论）
第 3~4 句：具体怎么走（关键动作、关键状态）
第 5 句：边界在哪 / 为什么这么设计（可选但强烈建议保留）
```

## 三、写法要求

### 1. 客观写实，不吹嘘

- 不说"革命性""颠覆""业界领先""一键搞定"
- 说清代价与限制：*"这一步需要人工复核口径，系统只负责把候选列出来"*
- 主动写明**能力边界**。用户发现边界时的信任度，远高于你主动说出来的

### 2. 术语出现即用比喻化解

面向不懂技术底层的观众。术语第一次出现时，紧跟一句白话或类比：

- *"本体（可以理解成这套系统对业务的词汇表）"*
- *"这一步做了幂等（同一个请求重复发十次，结果和发一次一样）"*
- *"只读接入，也就是只查不写，数据始终留在原来的库里"*

### 3. 数字化，别形容词化

| 别写 | 改写成 |
|---|---|
| 处理速度很快 | 单次处理在两秒内返回 |
| 支持多种数据源 | 支持 MySQL、Oracle、达梦三类数据库 |
| 覆盖了主要业务 | 覆盖下单、库存、结算三条主链路 |

### 4. 字幕友好（写的时候就要考虑）

字幕由配音的词级时间戳自动切分，单行最多 20 字，切分优先级是「句号 → 逗号 → 均分」。所以：

- **一句话控制在 20~40 字**。超过 40 字会被拆成两行字幕，虽然能拆，但节奏容易碎
- **多用句号，少用逗号和顿号堆叠**。连续三个顿号会切出很难看的断行
- **避免长串英文、URL、代码标识符**。中文 TTS 念英文缩写会逐字母念，字幕也不好断行
- **数字写成汉字读法更稳**：*"二十个指标"* 比 *"20 个指标"* 读得准（英文字母和阿拉伯数字混排时读音容易跳）
- 括号不要套两层

### 5. 不要写"接下来我们来看"

观众看得到画面。用内容本身过渡：*"第二件事是库存校验。"* 比 *"下面我们来看库存校验。"* 好。

## 四、narration.json 格式

写到 `<工程目录>/script/narration.json`：

```json
{
  "meta": {
    "voice": "zh-CN-YunyangNeural",
    "rate": "+6%",
    "fps": 30,
    "leadIn": 1.0,
    "gap": 0.7,
    "tail": 3.2,
    "title": "某某平台 · 订单模块",
    "srtName": "订单模块演示视频.srt"
  },
  "segments": [
    { "name": "片头",       "text": "……" },
    { "name": "整体架构",   "text": "……" },
    { "name": "订单受理",   "text": "……" },
    { "name": "库存校验",   "text": "……" },
    { "name": "结算对账",   "text": "……" },
    { "name": "收尾",       "text": "……" }
  ]
}
```

- `segments[].name` 会被 `storyboard.json` 引用，**改了名字记得同步改分镜**
- 顺序即播放顺序，段间自动插入 `gap` 秒静音
- 段落数量不限，但段数越多留白越多（每多一段多 0.7 秒）

## 五、写完之后

1. `python <skill>/scripts/build_audio.py --dir <工程> --dry` 看预估时长
2. 超了就先删，别先合成
3. 合成后 `解说稿.md` 和 `.srt` 会一并产出，把解说稿念一遍（或让用户过一遍）再进分镜

> **必做**：合成前把解说稿给用户确认。配音一旦生成，改文案就要重新合成 + 重新分镜 + 重新渲染，成本是分钟级的。
