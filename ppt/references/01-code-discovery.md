# 01 · 源码勘察：从代码读出「这份 deck 该讲什么」

目标不是"读懂代码"，而是**产出一份可汇报的业务大纲 + 一份可执行的核心功能清单**。

deck 的观众要听懂的是「这个系统在做什么、一条业务怎么走完、为什么这么设计、边界在哪」，不是类怎么继承。

> ### 先确认源码目录（第 1 个必问点）
>
> 开工前必须拿到**具体路径**，并问清四件事：
> 1. **单仓库还是多仓库**（前后端是否分开）—— 分开了要拿到两边的路径
> 2. **有没有要排除的目录**（`node_modules`、`dist`、`build`、`.venv`、`vendor`、第三方 SDK 源码）
> 3. **对应哪个分支 / 版本** —— deck 要对齐一个确定的版本
> 4. **本体模型 / 设计文档 / 需求文档在哪** —— 很多系统带 `models/`、`docs/`、`*.md` 规范文档。**这是提炼业务名词的金矿，优先级高于读代码逻辑**
>
> 拿到后先跑阶段 A，**把代码量与分层结构报给用户**再决定怎么读。

---

## 阶段 A：先摸清底细（10 分钟内完成）

按顺序做，不要跳。每一步都只取"能影响 deck 口径"的信息。

### A1 技术栈与规模

```bash
# 顶层清单
ls -la
# 依赖与语言（按存在的那几个看）
cat package.json pom.xml build.gradle requirements.txt go.mod composer.json pyproject.toml 2>/dev/null
# 目录树（只看两层，别急着深挖）
find . -maxdepth 2 -type d -not -path "*/node_modules/*" -not -path "*/.git/*" \
       -not -path "*/.venv/*" -not -path "*/dist/*" -not -path "*/target/*" | sort
# 代码量：判断是万行级小系统还是十万行级大系统
find . -type f \( -name "*.py" -o -name "*.java" -o -name "*.ts" -o -name "*.tsx" -o -name "*.js" -o -name "*.vue" \) \
     -not -path "*/node_modules/*" -not -path "*/.venv/*" | xargs wc -l 2>/dev/null | tail -1
```

| 代码量 | 读法 |
|---|---|
| < 3 万行 | 可以逐模块读，核心功能能挑到 10–15 个 |
| 3 万 ~ 15 万行 | 按"业务动作"抽，不看全部；核心功能控制在 8–12 个 |
| > 15 万行 | **必须先问用户要讲哪个子系统**，并把核心功能收到 8 个以内 |

### A2 找入口

| 形态 | 去哪找 |
|---|---|
| Spring Boot | 带 `@SpringBootApplication` 的类；`application.yml` 的 `context-path`；`@RestController` 上的 `@RequestMapping` |
| Flask | `Blueprint(...)` 的定义与 `url_prefix`；`@bp.route` / `@app.route`；`register_blueprints` |
| Django | `urls.py` 的 `urlpatterns`；`views.py`；`admin.py` |
| Node/Express | `app.js` / `server.ts` 里的 `app.use`；`routes/` 目录 |
| Vue / React | `src/router/index.*`；`src/views` / `src/pages`；`src/api/*` |
| 小程序 | `app.json` 的 `pages` / `tabBar` |
| 桌面 Electron | `src/main/index.ts`（主进程）、`preload`、`renderer/src/router` |
| 传统 Java Web | `web.xml`、`struts.xml`、`applicationContext.xml` |
| Python（FastAPI） | `app/routers/*`；`@router.get/post` |

**关键动作**：把入口清单按「业务动作」重排，不按技术层次排。见 A3。

### A3 提取业务名词（这一步最关键）

**业务名词藏在配置和模型里，不在代码逻辑里。** 按优先级读：

1. **本体模型 / 领域模型 YAML / TTL** —— 对象、行为、规则、状态、用例定义。**最高优先级**
2. **UI 模型 / 页面注册表 / 菜单配置** —— 几乎等于系统的功能清单，而且是被人挑过的措辞
3. **权限表 / 角色-资源映射** —— 能看出"谁的活"和"哪些动作是敏感的"
4. **枚举与数据字典常量** —— 状态机、类型、优先级。状态流转顺序往往就是主流程
5. **数据库 DDL 或实体类** —— 领域对象和它们的关系
6. **定时任务 / 消息队列消费者清单** —— 系统里"自动发生的那些事"
7. **外部接口对接清单**（`feign` / `HttpClient` / `requests` / `axios` 封装）—— 系统边界在哪
8. **需求文档 / README / 设计文档** —— 业务语言的最直接来源

把这些名词按"业务动作"聚合，而不是按"技术层次"聚合。

> 反例：*"这个模块用了工厂模式、策略模式，还有三层缓存"* —— 观众不关心。
> 正例：*"资料一提交就先走一遍合规校验，命中的直接拦下并给出原因；通过后自动派给下游角色，超时未处理会升级"* —— 这才是业务。

### A4 每条候选链路补四个信息

| 字段 | 从哪来 |
|---|---|
| 一句话定位 | 路由/菜单名 + 你自己的归纳（≤ 20 字） |
| 输入 | Controller 入参 / 事件消息体 / 定时任务触发条件 |
| 输出 | 写库了哪些表 / 发了什么消息 / 返回给前端什么 |
| 关键文件 | 3~8 个路径，作为 deck 里"技术结论的落点" |

## 阶段 B：核心功能的筛选（本技能的灵魂）

核心功能页是整份 deck 的主体（占 1/3 以上页数）。**判据不写死，AI 一定会挑错。**

### B1 三档判据

| 档 | 判据 | 处理 |
|---|---|---|
| **入选（核心）** | 至少满足一条：<br>① 承担**端到端主链路上的关键业务动作**（受理/审批/计算/流转/结算/对齐）<br>② 含**业务规则或状态机**（校验、上限、比例、状态推进、冲销）<br>③ 是**差异化价值点**（别家没有的、或本项目的技术亮点） | 进「核心功能」章节，**一页一个** |
| **排除（基础）** | 通用件：字典/编码/参数维护、用户/角色/权限管理、日志/监控、导出/打印、附件上传、消息通知 | 不进 deck；体量大时可并入「功能架构」页的模块清单 |
| **待定** | 拿不准它在链路中的位置 | 用一句判据：**「去掉它，业务链会不会断？」** 断 → 入选；不断 → 排除 |

### B2 硬约束：必须能落到一个界面

**每个核心功能都必须能指到一个看得见的界面**（页面 / 面板 / 弹窗）。理由：核心功能页的版式是"左讲解 + 右截图"，挑到没有界面的功能（纯后端守卫、注册表加载器、定时任务）就做不出这一页。

处理办法：

- 有界面 → 核心功能页
- 没界面但很重要（如事务边界控制、ID 生成器、审计留痕、定时任务 / 事件消费）→ **移到「技术架构」章节用架构图/序列图讲**，不占核心功能页

这条约束会自然地把"机制类"和"功能类"分开，deck 结构也更清楚。

### B3 数量与配比

| 场景 | 核心功能页数 |
|---|---|
| 短汇报 | 6 |
| **标准版（默认）** | **8–10** |
| 详细版 | 12–15（**硬上限 15**） |

超过 15 个候选时的收口办法：**合并同类项**（同一模块的多个子功能合成一页）、**升维**（把三个相似功能合成一页"某类操作的三条路径"）、**降级**（移到功能架构页的清单里）。

### B4 立项前必须跟用户对齐（对应第 2 个必问点）

把候选清单列出来，让用户选。下面是**格式示例** —— 编号、功能名、规则描述都要换成本次勘察的真实结果：

```
扫描到 N 个候选核心功能：

  A. <业务动作一>      <从源码读到的规则，如编号生成 / 唯一性校验>    建议 1 页
  B. <业务动作二>      <从源码读到的规则，如多条件组合筛选与列表>      建议 1 页
  C. <业务动作三>      <从源码读到的规则，如主从明细 + 关联记录>       建议 1 页
  D. <业务动作四>      <从源码读到的规则，如上限 / 配额 / 比例校验>    建议 1 页
  E. <业务动作五>      <从源码读到的规则，如状态推进 / 自动反算>       建议 1 页
  F. <业务动作六>      <从源码读到的规则，如归档 / 留痕>               建议 1 页
  G. <机制一>          ← 无独立界面，建议移到「技术架构」章节
  H. <机制二>          ← 无独立界面，建议移到「技术架构」章节

要讲哪些？也可以说"全都要"（会提醒页数上限）。
```

> ⚠️ **示例里的占位符一个都不许留在成品里。** 功能名、规则描述、`文件:行` 落点全部来自本次源码勘察；示例只是让你看清"清单长什么样"。

## 阶段 C：其他四章的内容怎么来

### C1 项目整体介绍（2 页）

- **第 1 页 · 系统定位**：一句话（业务语言，不含技术名词）+ 三个最突出的能力特征 + 三个关键数字（表数量 / 接口数 / 页面数，从代码里数出来）
- **第 2 页 · 工作台全景**（可选，看系统有没有整体界面）：主界面截图 + 三到四个构成区块说明

> 定位句的写法：**「这是一个把 X 从 A 做到 C 的系统」**。一句话只讲业务、不出现技术名词；把 X / A / C 换成你项目的主业务对象与首尾环节即可。

### C2 端到端业务流程（3 页）

一条**主链路**铺 3 页：
1. 主链路总览（泳道图 / 活动图）—— 跨角色跨系统的全过程
2. 前半段展开（阶段一到二）—— 关键校验与规则
3. 后半段展开（阶段三到四）+ 异常与状态分支

**找端到端链路的方法**：追四步 —— ① **触发点**（Controller 入口 / 定时任务 / MQ 消费者）② **写操作**（落到哪些表）③ **状态流转**（枚举取值怎么变）④ **人工介入点**（哪里需要人确认）。

一个系统通常有多条链路。**列出候选让用户挑一条主链路**，别自己拍板。

### C3 整体功能架构（2 页）

- **第 1 页 · 功能架构图**：用模板库 C·05（功能架构）或 C·03（应用架构），把功能按业务域分块
- **第 2 页 · 功能地图 + 本次重点**：同样的功能清单，但把**本 deck 要展开讲的核心功能高亮出来**，给后面 8–15 页做索引。这一页很值，观众能建立全局感

### C4 技术架构（2–3 页）

逐项都要有源码证据，**没找到证据的不写**：

| 要画的 | 从哪读 |
|---|---|
| 分层与目录结构 | 顶层目录 + 包结构 + 启动类 |
| 框架与依赖 | `requirements.txt` / `pom.xml` / `package.json`（**版本号要精确**） |
| 数据存储 | 连接配置、DDL / schema 定义、ORM 映射 |
| 中间件 | 依赖清单 + 配置文件（datasource / redis / kafka / mq） |
| 外部集成 | HTTP 客户端封装、SDK 调用点、端点与模型名 |
| 认证与安全 | 认证方式（session / token / JWT）、密码哈希、白名单守卫 |
| 部署形态 | Dockerfile / k8s yaml / nginx conf / 启动脚本 / 端口（**没有就不画部署视图**） |

**同时要记录"有哪些没有"**（无 Docker、无 ORM、无消息队列、无测试框架……）。这一条能防止 deck 编造，也是"能力边界"页的素材来源。

### C5 结语（2 页）

- **第 1 页 · 设计取舍与能力边界**：从代码里找出明确的限制（为什么写操作不开放、白名单边界、无回滚、单租户……），**主动写出来**。边界声明是可信度的来源
- **第 2 页 · 合规声明 + 落版**：「界面为按源码结构重绘的示意页面」+ 数据仿真声明 + 落版

## 检查清单

- [ ] 能一句话说清这个系统是干什么的（业务语言，不含技术名词）
- [ ] 核心功能清单已按 B1 三档筛过，且**每个都能落到一个界面**
- [ ] 核心功能页数在 8–15 之间
- [ ] 已把候选清单给用户确认过
- [ ] 端到端主链路已让用户挑过
- [ ] 每个技术架构结论都能指到文件:行

- [ ] deck 里不出现源码中的任何密钥 / 真实数据（**勘察时如果发现源码里有明文密钥，重点标注，deck 全程规避**）
